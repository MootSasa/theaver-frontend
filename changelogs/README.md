# Changelog Fragments Guide / Правила оформления Changelog

Заметки о новых версиях Theaver показываются одновременно в четырёх местах:
1. В диалоге обновления внутри клиента (`Обновление` / `What's New`).
2. В push- и системных уведомлениях о выходе новой сборки.
3. На странице [theaver.app/changelog](https://theaver.app/changelog) (`RU` и `EN`).
4. На странице [GitHub Releases](https://github.com/MootSasa/theaver-frontend/releases) (где внизу дополнительно прикрепляется свёрнутый технический список коммитов).

Поэтому вместо сырого вывода `git log` мы пишем короткие двуязычные фрагменты в `changelogs/fragments/<topic-slug>.md`.

---

## Как добавить запись в своей ветке

1. Скопируйте [`TEMPLATE.md`](./TEMPLATE.md) в `changelogs/fragments/<topic-slug>.md` (например, `changelogs/fragments/voice-noise-suppression.md`).
2. Укажите `type`:
   - `added` — новая заметная возможность (`✨ Новое` / `Added`)
   - `improved` — улучшение интерфейса, скорости, удобства (`⚡ Улучшения` / `Improved`)
   - `fixed` — исправление ошибки, с которой сталкивались пользователи (`🐛 Исправления` / `Fixed`)
   - `security` — важное для пользователей улучшение безопасности (`🔒 Безопасность` / `Security`)
3. Заполните `summary_ru` и `summary_en` — по одной короткой строке без Markdown (`**`, `` ` ``, `#`). Этот текст пойдёт в push-уведомления и заголовок карточки на сайте.
4. Под заголовками `### ru` и `### en` напишите **1–3 пункта** (`- ...`) о том, что изменилось с точки зрения пользователя.
5. Проверьте схему локально:

   ```bash
   python3 scripts/calculate_release.py --validate-fragments
   ```

## Редакционные правила

### О чём писать и о чём НЕ писать

- **Пишите о видимом результате:** объединяйте серию коммитов по одной задаче в один понятный пункт.
- **Не включайте:**
  - внутренний рефакторинг, переименование классов и перестановку файлов;
  - unit- и widget-тесты;
  - правки CI/CD, Docker, скриптов сборки и обновления `pubspec.yaml`;
  - исправление бага, который появился и был закрыт внутри той же невыпущенной ветки;
  - технические скоупы (`**tiling**:`) и SHA-хэши коммитов (`(efa8fc95)`).
- Для правок без видимого эффекта фрагмент не нужен — укажите `[no-changelog]` в описании PR.

### Примеры: плохо / хорошо

- **Плохо:** `- **tiling**: wrap workspace scaffold and emoji panel in Material to prevent fallback underline text style (efa8fc95)`
- **Хорошо:** `- **Панель эмодзи:** убрано случайное жёлтое подчёркивание текста в окне чата на компьютере.` / `- **Emoji panel:** fixed stray yellow text underlines in the desktop chat workspace.`

- **Плохо:** `- **account**: add POST /api/security/account/delete/confirm and SecurityScreen dialog`
- **Хорошо:** `- **Удаление аккаунта:** в настройках безопасности появилось самостоятельное удаление аккаунта с кодом на почту и 7-дневным периодом отмены.`

## Как релизный скрипт выбирает фрагменты

`scripts/calculate_release.py` определяет тег предыдущего релиза и собирает фрагменты из `changelogs/fragments/*.md`, добавленные или изменённые командой `git diff --diff-filter=AM <tag>..HEAD`:

- Для канала **`beta`** сравнивается `latest_tag..HEAD` (попадают только изменения после прошлой бета-сборки).
- Для канала **`stable`** сравнивается `latest_stable_tag..HEAD` (автоматически объединяются все фрагменты, вышедшие в бетах со времени прошлого стабильного релиза).
- Удалять файлы фрагментов после релиза вручную или авто-коммитом из CI **не нужно**.
